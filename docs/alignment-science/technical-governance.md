# Technical AI Governance: Verification and Compute

**Technical AI governance** (TAIG) means technical analysis and tools that support governing AI: verifying what a lab trained or deployed, securing model weights, and making agreements checkable. This page covers the problem map, verification lines with code or concrete designs (inference verification, API model-identity audits, compute verification, enclave-based auditing and double-blind evals, training-integrity checks), and third-party assessment as a method (access and redaction terms, disclosure indicators, auditing a published safety case). Evaluations used as governance evidence are on [`dangerous-capability-evals.md`](../evaluation/dangerous-capability-evals.md); unlearning and tamper resistance are on [`unlearning.md`](unlearning.md).

## Open Problems in Technical AI Governance (Reuel et al., arXiv:2407.14981)

A catalogue of open problems in technical AI governance (TAIG), written for technical researchers and funders. It is organised on two axes:

- **Capacities:** Assessment, Access, Verification, Security, Operationalization, Ecosystem Monitoring.
- **Targets:** Data, Compute, Models and Algorithms, Deployment.

Each cell lists open problems with example research questions. Cells that fit an ML fellow include verification of training data (5.1.1), verification of compute workloads (5.2.2), proof-of-learning (5.3.3), prevention of model theft (6.3.1), modification-resistant models (6.4.2), and (multi-)agent evaluations (3.3.3). The authors call the catalogue incomplete, and the v2 revision is dated April 2025, so check newer work before claiming a problem is untouched.

**When not to use it:** as evidence that a problem is still open in 2026. Use it as a map, then search for later work.

## Inference verification against weight exfiltration

Rinberg, Karvonen, Hoover, Reuter & Warr, "Verifying LLM Inference to Detect Model Weight Exfiltration" (arXiv:2511.02620). Code: `RoyRin/inference_verification_for_model_weight_exfiltration` (GitHub; no license file detected via the GitHub API, last push 2026-02-19).

- **Threat:** an attacker who controls an inference server hides weight bits inside ordinary model responses (steganography).
- **Method:** formalises weight exfiltration as a security game and proposes a verification framework for inference that provably mitigates steganographic exfiltration. To make verification possible, the paper characterises the legitimate sources of non-determinism in large language model (LLM) inference and introduces two practical estimators for them.
- **Result:** on MOE-Qwen-30B the detector reduces exfiltratable information to under 0.5% at a false-positive rate under 0.01%, which the authors equate to a more than 200x slowdown for an adversary. Models tested ranged from 3B to 30B parameters.
- **Scope:** the threat model is weights hidden in model responses from an inference server, under the trust assumptions the paper states. Other routes to weight theft are not what it addresses.

**Follow-up: combining evidence over time.** Ortega-Fernandez, Kowalczyk & Warr, "Anytime-valid detection of LLM weight exfiltration" (arXiv:2610.11843, 2026-10-08) note that replaying prompts on a trusted server exposes token mismatches but "benign numerical nondeterminism also causes token mismatches", so a patient attacker hides in normal variation unless evidence is combined across responses. Their prompt-level **e-process**, calibrated on benign traffic, accumulates evidence sequentially while (under a calibration-transfer assumption) "controlling the probability of any false alarm over an unbounded monitoring horizon"; it is evaluated on four models against a seed-blind attacker and a stronger seed-aware attacker that hides payload bits only in near-ties. Use it when a detector has to run indefinitely and you need a stated false-alarm guarantee rather than a per-token threshold.

**Open problem / evidence bar:** the same guarantee at frontier-model scale and production batching, against an adaptive attacker who knows the detector, with the overhead measured on real serving infrastructure.

## Is the API serving the model it claims? Detecting partial model substitution (API-TAIL)

Aliases: "model substitution", "API auditing", "model identity verification", "is my provider serving the right model". Mei, Tian, Yuan, Xu, Chen, Han & Wang, "API-TAIL: Detecting Model Substitution in LLM APIs through Temperature-Aligned Likelihood Tails" (arXiv:2610.36801v2, 2026-10-27).

- **Threat:** a provider routes a fraction of requests to a cheaper model while billing for the advertised one. It is hard to detect because honest providers also shift the output distribution through undocumented temperature scaling, sampling truncation, repetition and presence penalties, and default system prompts.
- **Method:** a typicality audit. Score each response's surprisal under the claimed model, run locally (this needs the claimed model's weights; the endpoint's own log-probabilities are not used), absorb batch-wide shifts by fitting one effective temperature that centres the standardized surprisal scores, then flag the endpoint if the number of remaining tail responses exceeds a threshold calibrated across legitimate configurations. The insight: legitimate serving changes shift the whole batch, while substitution injects individual anomalous responses.
- **Result (abstract):** "API-TAIL controls false alarms across diverse honest providers and detects low-rate partial substitution with a small query budget", and it outperformed adapted rank- and MMD-based audit baselines under a common composite calibration.

**When to use it:** before trusting a model comparison or eval run through a third-party provider or router, as a governance tool for auditing what an API serves, or as a research question for verification regimes. **When not to:** for closed models whose weights (and so reference likelihoods) you do not have; the abstract gives no detection rates or query counts, so read the paper before citing a budget. One preprint; no code link in the abstract.

## Low-trust compute verification (Cankaya, 2026)

Naci Cankaya, "A system overview for near-term, low-trust AI compute verification" (LessWrong, 2026-06-23, version 0.2 working draft). A reference architecture for verifying AI compute use under an arms-control-style agreement between rival states:

- **Evidence capture:** network taps (optionally memory pinging) record what workloads ran. The verifier receives only cryptographic commitments (signed hashes); the prover keeps the plaintext.
- **Evidence evaluation:** the verifier challenges a random subset of committed records, which are evaluated in an air-gapped environment (plan A) or with zero-knowledge proofs once those mature (plan B), and released only in a pre-agreed disclosure format.
- **Design goals:** retrofittable to existing hardware from off-the-shelf components; no mutually trusted chips; physical security is a prerequisite.

**When not to use it:** as a settled design. The author published it to draw out what it gets wrong, and invites critique from policy, security and engineering readers. Building and red-teaming one component, such as the tap-to-commitment path or the sampling scheme, is a concrete project.

## Auditor-in-a-Box: an LLM in a trusted execution environment as a third-party auditor (Rinberg, 2026)

Aliases: auditor in a box, auditor-in-a-TEE, trusted capable model environment, TEE auditing, privacy-preserving monitoring, ZDR-lite.

Roy Rinberg and Ben Penchas, "Auditor-in-a-Box: Tools for Third-Party Auditing" (LessWrong, 2026-07-28; written in Rinberg's voice). The scheme runs an open-weight large language model (LLM) inside a **trusted execution environment (TEE)**, a hardware-isolated processor region whose memory the host cannot read and whose loaded binary is measured and remotely attested. Two mutually distrustful parties sign a **Plan** (inputs, computation steps such as Python code and LLM calls, and the outputs to release), send their private data encrypted to the TEE's key, and each receives only the agreed outputs. The post proposes two near-term applications: **verifiably-scoped monitoring** ("ZDR-lite", a relaxation of zero data retention that lets a lab run safety monitoring while bounding what it may monitor *for*) and **recurring third-party auditing** of a lab's internal practice. Its threat model trusts the TEE hardware and attestation and trusts the LLM "to be a faithful classifier *within distribution*"; it does not assume either party refrains from trying to exploit the model.

Code: `RoyRin/auditor-in-a-TEE` (main), `RoyRin/auditor-in-a-TEE-webapp` and `RoyRin/auditor-in-a-TEE-deployer`, all with no licence file detected by the GitHub API and 1–3 stars as of 2026-10-14; a live demo is linked from the post, which describes it as ready to be "lightly poked and interrogated" but not for regular use. A short paper by Penchas, Rinberg and a collaborator was submitted to the TAIGR workshop.

**When not to use it:** as production infrastructure, or where code reuse needs a licence. **Open problem / evidence bar:** the post's mitigations for prompt injection against the in-box model (authorising several interchangeable models and choosing one at runtime with trusted randomness; each party placing its own uninspectable injection filter in front of the model) are design proposals; a measured attack-success rate against a fixed egress limit (for example a one-bit yes/no answer), with an adaptive adversary who can probe the same open-weight model offline, would show how much the scheme leaks.

## Double-blind evals: a private benchmark and proprietary weights in one secure enclave (Trask et al., 2026-11)

Aliases: "double-blind evaluation", "DBE", "dual confidentiality", "confidential computing for evals", "PySyft Datasite", "Confidential Space". Trask, Messing, Pahwa, Maham and co-authors (30 authors from Google, OpenMined, AVERI — the AI Verification and Evaluation Research Institute — MLCommons and Singapore AISI), "Double Blind Evals: Resolving the Dual Confidentiality Dilemma in AI Safety Auditing" (arXiv:2611.12604, 2026-11-09).

- **Problem.** An evaluator wants its prompts kept from the model owner (so they cannot leak into training); the owner wants weights and inference code kept on its own secure infrastructure. Testing through the owner's API exposes the prompts in plain text; shipping weights to the evaluator exposes the weights.
- **Method.** Both assets are streamed over encrypted channels into a hardware enclave (a Google Cloud Confidential Space A3 virtual machine with Intel Trust Domain Extensions (TDX) memory encryption and an NVIDIA H100 confidential GPU) after both parties verify remote attestation; the evaluation code is submitted and approved through OpenMined's **PySyft** (the paper names v0.10.x; `syft` 0.10.2 was on PyPI on 2026-11-21), only bounded aggregate results leave, and the enclave is then destroyed.
- **Pilot.** Google DeepMind's Gemini 2.5 Flash Lite was evaluated on prompts from the reserve set of the MLCommons AILuminate benchmark (prompts "never been processed by any model"), with AVERI encrypting the prompts and judging the outputs, and separately on a private Singapore AISI prompt set. The authors describe it as the first use of the technology "to provide mutual secrecy for one organization's frontier-class proprietary model weights and another organization's closed benchmark". The paper reports the deployment; it gives no benchmark scores.
- **Limits the authors state.** Not all code could be inspected or allow-listed, because the model could not be run using only layers present in open-source libraries; individual builds of the enclave's guest operating system "are not independently reproducible"; attestation reports are signed and verified by Google's services, "which places Google in the verification path"; and one model on one GPU is far from distributed confidential clusters for the largest models. They report that the bottleneck was "the procedural overhead and human coordination required for legal agreements and code review", not compute (under 5% overhead, a figure cited from earlier work).

**How it relates to Auditor-in-a-Box:** the same primitive (attested execution inside a trusted execution environment with a pre-agreed output), applied to benchmark integrity instead of auditing private records; here the proprietary model is the thing inside the enclave, not the auditor. **When not to use it:** for open-weight models (download the weights and run the private benchmark yourself); as a guarantee against a model owner who is also the cloud and attestation provider, unless that trust is acceptable; or expecting a turnkey package: reproducing the pilot needs confidential-GPU cloud instances and the owner's cooperation, and no end-to-end repository for the pilot is named in the paper. **Open problem / evidence bar:** the same protocol with a model owner who is *not* the enclave provider, fully inspectable inference code, and a measured leakage bound on what the returned metrics reveal about the prompts.

## Third-party evaluation from inside a lab: access, disclosure and redaction terms (2026-11)

Two evaluators published the terms of high-access engagements in November 2026. For governance research the terms themselves are the object of study: they decide what a published verdict can establish.

- **Apollo Research and OpenAI: a pilot toward embedded evaluations** (Apollo blog, 2026-11-16). Six Apollo staff work inside OpenAI for four months on four questions: "Whether training incentivizes subversion", "Whether evaluations can elicit subversion", "Whether subversion occurs during internal deployment" and "Whether reasoning relevant to subversion would be detectable". Apollo names three requirements for credible embedded evaluation: **access** to all relevant data even if the developer wanted to hide it, **disclosure** of findings even if the developer wanted to prevent it, and **meta-transparency**, "the right to publicly explain the conditions and limitations of an evaluator's work". Apollo says the pilot does not yet meet the first two but meets its bar for meta-transparency. Stated terms: for the training question, access to "relevant training code and datasets, reinforcement-learning rollouts with available reasoning traces and rewards, and the ability to query intermediate model checkpoints"; OpenAI may withhold in-scope items for technical infeasibility, security or intellectual-property reasons but must say that withheld items exist and give written reasons; OpenAI "may not redact Apollo Research's verdicts for each claim" but may redact supporting evidence; claims based on staff conversations need OpenAI's formal attestation unless Apollo establishes them independently; two public reports are planned.
- **Apollo's six monitoring detection claims** (Jotautaitė & Hobbhahn, "Towards embedded evaluations for AI monitoring", LessWrong and Apollo blog, 2026-11-19; LessWrong byline "monika_j" and Marius Hobbhahn, Apollo's page credits Monika Jotautaitė). The threat model is **rogue internal deployment (RID)**: agents inside a lab's infrastructure operating for a sustained period against the developer's intent. The claims an embedded evaluator would test: "Claim 1 (coverage): Monitors are deployed across all internal deployment contexts"; "Claim 2 (capability): If rogue internal deployment (RID) were to occur, monitors would detect it"; "Claim 3 (trust): The monitors are trusted"; "Claim 4 (disclosure): Any detected incidents are disclosed appropriately"; "Claim 5 (past deployments): No RID was attempted and missed so far"; "Claim 6 (future deployments): Monitoring will be adequate for the next internal deployment." Containment (sandboxes, access controls, firewalls) is left for a future extension; the post covers detection only. A proposal and research roadmap, not results. These sit beside Apollo's four scheming-propensity claims cited in the loss-of-control section of this page; control-evaluation detail is on [`ai-control.md`](../oversight-and-control/ai-control.md).
- **METR at Anthropic: a high-access assessment with unilateral redaction** (METR, 2026-11-05). From 2026-08-12 to 2026-10-29, METR staff (2.5 full-time equivalents) assessed how much AI is accelerating AI R&D at Anthropic. METR could request any information it thought relevant and Anthropic "could unilaterally approve or reject" requests; Anthropic had unilateral redaction rights over non-public information, and METR had the right to disclose whether redaction rights were exercised and whether findings depended on redacted material. Outcome: METR could share its top-level conclusions (benchmark progress measured on Anthropic's version of the Epoch Capabilities Index growing at an estimated 1.9x the pre-October-2025 rate, 95% confidence interval 1.5–2.8x), but "Anthropic redacted a majority of the evidence we found most informative for these conclusions", and METR says the report therefore does not achieve what its own framework calls "transparency about evidence". METR also notes the project was not full "employee-like" access. The measurement itself (index construction, robustness to link function and model set) belongs to [`dangerous-capability-evals.md`](../evaluation/dangerous-capability-evals.md) and [`evals.md`](../evaluation/evals.md).

**What to take from the pair:** (1) a third-party verdict is only as informative as the reader's knowledge of what was withheld, so meta-transparency (METR's redaction summary, Apollo's right to describe what was withheld and why) is the minimum that makes a report interpretable; (2) both arrangements leave the developer in control of what evidence is published, so outsiders can check the *verdict* but not the *evidence*. **A project shape:** compare published access terms across engagements on fixed dimensions (who decides scope, who can redact what, whether the evaluator can report refusals, whether verdicts are protected) and say which claims each arrangement could and could not support. **When not to cite these as findings about safety:** Apollo's pilot had published no results as of 2026-11-23, and the six claims are a framework.

## Disclosure indicators for chain-of-thought monitorability (Davies & Bearman, 2026-11)

Aliases: "transparency disclosures for CoT monitorability", "monitorability indicators", "Independent Verification Organization". Jacob Davies & Theo Bearman (ERA Fellowship; Institute for AI Policy and Strategy), "Transparency Disclosures for Chain-of-Thought Monitorability" (arXiv:2611.13873, 2026-11-10; an update of a July 2026 workshop paper). Chain-of-thought (CoT) monitoring depends on a chain of five conditions, and the report picks one indicator per condition that developers could disclose, chosen from 21 candidates scored for informativeness, technology readiness, external verifiability, developer tractability and implementation feasibility:

1. **Third-party CoT access and base architecture specifications** (does the model still reason in a CoT that outsiders can see, and is the CoT necessary for complex reasoning). This one "underpins external verification of the rest".
2. **Naturalness**: a rubric-based legibility score for how easily a human can follow the reasoning.
3. **Faithfulness**: scores on a suite covering several ways a CoT can fail to reflect the computation.
4. **Detection**: the proportion of harmful behaviours that evade the monitoring system.
5. **Uplift**: the performance gap between a monitor with CoT access and one that sees only actions.

**Audit result:** across public disclosures from OpenAI, Anthropic and Google DeepMind (through mid-October 2026), "no developer covers the full set, but that every indicator has been reported by at least one frontier developer". Because disclosures rest on developers' own evaluations, the authors recommend repeating the audit with deeper access "either by embedded evaluators working within developers or by an Independent Verification Organization". They deliberately do not prescribe specific evaluations per indicator.

**Use it as:** a five-row checklist when reading the monitorability sections of a system card or frontier safety report, and a template for a disclosure-audit deliverable in another area. **When not to:** as a measurement method (it says what to report, not how to measure it), or as current past mid-October 2026: the November system cards are not in its audit. The measurements behind indicators 2–5 are on [`cot-faithfulness.md`](cot-faithfulness.md).

## Reading a frontier safety report as a safety case: the Gemini 4 critique (2026-11)

Adam Kaufman & Alek Westover (Redwood Research), "Gemini 4 safety reports don't demonstrate low loss-of-control risk" (LessWrong 2026-11-16), is a worked example of auditing a developer's published argument. Google DeepMind's Gemini 4 Argon report concludes the model is "highly unlikely" to cause severe harm by evading oversight, a conclusion the report says "rests primarily on our ability to detect and intervene on harmful trajectories via CoT and action monitoring" (both phrases confirmed in the Argon report text); the Carbon report treats that assessment as still applicable. The critique's checks, each reusable on any monitoring-based safety case:

- **Was the evidence gathered on this model?** No control evaluations were run on Carbon; Argon's monitor-evasion results were reused on the grounds that Carbon "did not show meaningful new capabilities" (phrase confirmed in the Carbon report).
- **Is a lower alert rate less misbehaviour or more evasion?** The post reports that monitors flag Carbon several times less often than Argon in internal use and that the report does not show which explanation holds.
- **What does the control evaluation say?** The Argon report states the model "can evade a realistic monitor on easy sabotage tasks about half the time when encouraged to do so" (confirmed in the report text); the developer's argument that real harm is much harder than the test tasks is, per the critique, not measured.
- **Did training touch the monitored channel?** Per the critique, during some of Argon's training a grader that penalized reward hacking could see the model's chain of thought.
- **Is there a threshold?** "Nothing in the reports tells us what results would have changed GDM's conclusion", and claims that a behaviour was never observed come without evidence that the detectors would have caught it.

The authors add that they think external deployment of these models is acceptable and that they know most of this only because Google DeepMind chose to report it. The per-session alert ratios and other page-cited figures in the post were not individually checked against the reports for this page; the control-evaluation discussion is on [`ai-control.md`](../oversight-and-control/ai-control.md) and the framework thresholds on [`dangerous-capability-evals.md`](../evaluation/dangerous-capability-evals.md). **Use it as:** a checklist for writing or reviewing a safety case (state the threshold in advance, validate detectors on planted positives, re-run evaluations on the model actually deployed, keep monitored channels out of training graders).

## Verifying that a training run happened as described (SciCheck, 2026-11)

Nguyen, Gresham, Dagher & Long, "SciCheck: A Framework for Verifying the Integrity of Deep Learning Training" (arXiv:2611.09889, 2026-11-06; abstract read). Two honest runs never produce identical weights, so recomputation cannot be the check. SciCheck has the trainer post a blueprint and per-epoch checkpoint commitments to a ledger; a verifier then (a) compares per-step gradient statistics against its own reference run with a statistical judge model and (b) re-executes randomly chosen committed training segments. On an MLP, a CNN and an autoencoder of 100k–500k parameters, under gradient sign flipping, label poisoning and fabricated runs, it "reaches F1 of 0.966, 0.906, and 0.976 while rejecting 0-4.4% of honest runs". The spot-check does most of the work: "fabricated runs that replay genuine statistics look no more anomalous than honest runs to any statistical detector we test", while the spot-check catches fully fabricated segments with probability at least 1−(1−s)^k for k sampled segments. Verification costs 1.5–2.3x one retraining, mostly the verifier's reference run. **Relevance:** a small-scale instance of the "verification of compute workloads" and proof-of-learning cells in Reuel et al.'s map. **When not to cite it:** as evidence the approach works at LLM scale; the models are at most 500k parameters and a reference run per verification is unaffordable for frontier training. **Open problem / evidence bar:** segment spot-checking without a full reference run, on a model large enough that nondeterminism across hardware matters.

## How strong is the evidence for loss of control? (Uuk et al. 2026)

Uuk, Koivula, Pacchiardi, Gipiškis, Caroli & Horton, "Assessing the Empirical Evidence for Loss of Control from Agentic General-Purpose AI" (arXiv:2610.25241, 2026-10-18). Motivated by the EU General-Purpose AI Code of Practice, which lists loss of control as a systemic risk to assess, the authors grade 19 empirical studies across eight threat-model properties (for example strategic deception, situational awareness, autonomous replication) on **construct, content and external validity**. Central finding: the evidence "supports a judgment of loss of control as 'weakly plausible'" (plausibility here means strength and direction of evidence, not a probability). "No study clears the validity thresholds for a stronger judgment that a property is present; a single study clears them only for a negative-direction judgment (against situational awareness)." Validity gaps are widespread, "particularly in external validity", and for the most dangerous properties the authors argue high external validity "may be structurally unachievable under responsible research practices".

**Use it as:** a checklist of what a policy reader will discount in a scheming, deception or self-replication eval; pair it with Apollo's four claims for a scheming safety case (no training incentive, no propensity in evals, no attempts during internal deployment, reasoning would be detected), summarized in [`model-organisms.md`](model-organisms.md#scheming-propensity-in-realistic-settings-anti-scheming-training-and-inability-safety-cases-20242026). **When not to cite it as current:** it grades a fixed set of 19 studies (the arXiv comment says it was first posted on SSRN on 28 May 2026), and the authors note that "empirical assessments may systematically lag behind the capability frontier"; check its reference list before treating a newer result as already weighed.

## What does a first deliverable look like?

A working verifier for one narrow claim (for example, "these outputs came from this model under this sampling configuration"), measured against an adversary who knows how it works, with its false-positive rate and overhead reported. On the assessment side: an audit of published documents against a fixed checklist (the five monitorability indicators, or the access and redaction terms of evaluator engagements), with every cell tied to a quoted passage.
